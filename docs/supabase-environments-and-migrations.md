# Supabase environments and migration lifecycle

Status: WBS 1.4 implementation in progress. Hosted project identifiers and
credentials remain outside source control.

## Environment boundary

Development, test, and production use three independent Supabase projects.
Suggested names are `canwin-crm-dev`, `canwin-crm-test`, and `canwin-crm-prod`;
the user must approve the organization, region, current cost, and each creation
before the external write occurs.

| Environment | Data | Purpose | Hosted write rule |
| --- | --- | --- | --- |
| dev | Synthetic/developer-created only | Interactive engineering | User-approved project; reviewed migrations only |
| test | Deterministic synthetic only | Automated integration/UAT preparation | Separate project and credentials; resettable |
| prod | Approved live records only | Production service | Gate 5 plus exact production migration approval |

## Free-plan operating posture

The three CRM environments exist as independent Tokyo-region projects. The
legacy Team OS 3.0 project must remain active and must never be paused by this
procedure. Supabase Free Plan limits the account to two active projects across
organizations; paused projects do not count toward that limit. Until a paid
plan is explicitly approved, use this operating posture:

| Project | Normal state before CRM launch | Rule |
| --- | --- | --- |
| Team OS 3.0 | Active | Never pause or modify from the CRM repository |
| `canwin-crm-dev` | Active | Default CRM engineering environment |
| `canwin-crm-test` | Paused | Restore only for an approved test window; pause again before restoring another CRM environment |
| `canwin-crm-prod` | Paused | Restore only for production readiness or an approved release window |

Only one CRM project may be active alongside Team OS 3.0. Before restoring a
paused CRM project, verify that the currently active CRM project has finished
pausing. After a test or release window, collect migration/advisor evidence,
pause that project, and restore development. A paused Free Plan project has a
90-day one-click restore window, so the project owner must either restore it
within that window or follow Supabase's documented backup recovery path. No
keep-alive traffic may be generated merely to bypass platform pausing rules.

Project references, URLs, publishable keys, secret keys, database passwords,
access tokens, and connection strings are injected from environment-scoped
secret stores. They are never committed. Promotion means applying the same
immutable migration sequence to the next environment, never copying a database
or key set.

## Source of truth

- The pinned CLI version in `package.json` and `package-lock.json` defines the
  migration toolchain.
- `supabase/config.toml` is generated by that CLI and reviewed in Git.
- `supabase/migrations` is the append-only schema history.
- `supabase/seed.sql` contains data inserts only and runs after all migrations.
- Dashboard-only schema changes are prohibited. If emergency investigation
  changes a non-production database, reconcile it into a reviewed migration
  before any promotion.

## Creating and validating a migration

1. Update the branch from `main` and run `npm.cmd run check`.
2. Create the file with `npm.cmd exec -- supabase migration new -- <name>`.
   Never invent the timestamp or filename.
3. Review SQL for dependencies, privileges, exposed-schema RLS, view security,
   function execution grants, destructive operations, and compatibility.
4. With Docker and local-port approval, start the local stack and run
   `npm.cmd exec -- supabase db reset --local`.
5. Run database tests and `npm.cmd exec -- supabase migration list --local`.
6. Confirm a clean schema diff and attach sanitized evidence to the PR.

## Hosted promotion and consistency

Before any hosted write, record the environment, project ref (masked in public
evidence), migration versions, commit SHA, CLI version, operator, approval ID,
expected change, backup/recovery posture, and validation queries. Compare local
and hosted migration lists; a timestamp missing, extra, or reordered on either
side is drift and blocks promotion.

Dev and test changes require explicit project authorization. Production schema
or data migrations require an `APR-MIG-###` bound to the exact project,
migration set, commit, evidence, time window, and one-time use. RLS/Auth,
privileged functions, or Storage policies additionally require security review.

## Rollback policy

Local, unshared work may reset to an earlier version and regenerate a migration.
After a migration is deployed anywhere, history is immutable. Rollback is a new
forward migration, preferably expand/contract:

1. Add compatible structures or behavior.
2. Deploy consumers that tolerate both versions.
3. Backfill with observable, restartable jobs when needed.
4. Verify counts, constraints, hashes, permissions, and application behavior.
5. Remove obsolete structures only under a separately reviewed destructive
   migration and exact approval.

Backups/PITR are incident recovery controls, not the normal way to undo a schema
release. On migration failure, stop further promotion and writes in scope,
preserve evidence, then execute only the approved forward-fix or recovery plan.
